## applicability

适用于使用 OpenSpec 管理开发变更的工作：用户可能只有一个问题，也可能已经有 baseline、进行中的 change、部分工件、实施结果或验证意见，需要根据现状继续推进。

本策略只组织以下七个 Skill：

| 用户称呼 | 完整 Skill 名称 | 负责的具体工作 |
| --- | --- | --- |
| explore | openspec-explore | 理解架构、调查问题、澄清要求、比较方案 |
| new | openspec-new-change | 建立 change scaffold，取得首个工件说明 |
| continue | openspec-continue-change | 按实际 schema 每次创建一个就绪工件 |
| apply | openspec-apply-change | 从未完成任务开始实施 |
| verify | openspec-verify-change | 检查完整性、正确性、一致性并分级报告 |
| sync | openspec-sync-specs | 将 delta specs 合入 main specs |
| archive | openspec-archive-change | 检查收尾状态并归档 change |

适用前提是能够定位目标工作区、相关 OpenSpec 材料及拟使用 Skill 的完整原文，执行环境满足该 Skill 的工具要求。已经有 change 时，继续其真实状态，不以采用策略为由重新建 change。

用户始终通过 Patrol 表达目标、问题、批准和反馈。Patrol 选择 Skill 和承接工作的 Context；用户不必选择线程、提供 Context ID 或依次输入命令。必要澄清针对目标、变更对象和行动边界，由 Patrol 在同一入口提出。

本策略与原 Skill 配合使用。原 Skill 的全文、必要资源、工具步骤、模板、只读限制、确认要求和停止条件全部保留；下文是调用与组织规则，不能代替原 Skill。只导入 STRATEGY.md 不会安装这七个 Skill，也不会把资源目录注册成可执行 Skill；执行前须确认原文和资源实际可读。

已有材料能够直接回答的问题，不必启动完整开发安排。已有任务、工件或证据足够且仍有效时，复用结果；不为了形式完整而补跑七个 Skill。普通修改若不涉及 OpenSpec 变更管理，可继续已有工作方法。未决定开发的探索可以止于理解，不必生成 change。

## evolution

### 共同的调度规则

1. 每轮以最新有效目标、授权、反馈、OpenSpec 状态及真实执行结果判断下一项需要解决的问题。Context 是持续工作线，Run 是一次执行，Round 是重新观察和安排的轮次。七个 Skill 是可组合的工作方法，不是七个固定阶段或七条固定线程。
2. 优先复用已掌握该 capability、change 或问题的 Context。同一 Context 可以先 explore，再 new、continue、apply；一次 verify 或 sync 也可以回到该 Context。只有独立探索历史、隔离实施或独立验证确有价值时才派生，并写清其问题、输入、可编辑范围、依赖及停止条件。
3. 派生前先查已有承接者和真实进展。目标 change、Skill、输入版本与任务范围相同且已有执行进行中时，等待或补充相关信息，不再开同一份工作。多个工作线涉及同一工件、代码区域或 main spec 时，明确写入归属和先后关系；隔离工作树也不能免除结果汇合时的冲突检查。
4. 读取 main specs 以了解 baseline，再按目标读取实际代码和相关历史。单纯补齐背景不必都调用 explore；已有理解足够时直接处理当前问题。baseline 是已有规范，实际实现需要另外检查，不能仅凭规范声称代码已经符合。
5. 原 Skill 的执行步骤由承接 Context 在 Run 中完整执行。读取选定版本的 SKILL.md 全文及必要资源，按 CLI 的状态、instructions 和真实路径操作；不能仅凭本策略的概括执行。Skill 缺失、资源不可访问或命令失败时报告具体阻碍，不编造状态或改用猜测路径。
6. 一次 Skill 完成或暂停后，向 Patrol 返回实际结果和下一步条件。后续工作只在前置结果真实产生、适用且授权有效时安排；不能把“计划创建”“建议验证”“准备同步”当成已经完成。关键顺序、只读范围和审批边界要写进实际任务约束并检查证据，策略文字本身不提供系统保证。
7. 停止条件也是结果。new 展示首个模板后停止；continue 每次完成一个工件后停止；explore 不自行转入实施。用户明确要求“生成后停下”“先只报告”“不要建议”“不要改代码”时，Patrol 不得通过新 Run 或新 Context 绕开。已有明确授权可在其范围内组织工作，但不能用笼统目标、安装策略或工件齐全代替原 Skill 要求的方向确认。
8. 对 continue、verify、sync、archive，Patrol 应把用户已经明确绑定的 change 作为显式输入传给 Skill；未提供明确名称且源 Skill 要求选择时，在 Patrol 中列出候选并让用户决定，不凭最近修改时间猜选。apply 可按其原文处理唯一活动 change。用户选择的是变更对象，不是线程。

### explore：需要理解时调查

**什么时候使用：** 目标或方案尚不清楚，需要理解现有架构、追踪问题、核实假设、比较方案；实施中遇到新的设计疑问，也可以回到 explore。

**什么时候不用：** 已有足够理解和有效决定，只缺生成工件、实施或报告；不能把它当成每个 change 的固定开场，也不能用 explore 承接代码修复。

**前置条件和输入：** 当前问题、用户希望本次讨论达到的范围、相关 baseline、代码、现有 change 和未知项。若用户只要求“读清架构，不要提建议”，本次目标就是形成理解与必要事实。

**在哪个 Context 执行：** 默认在已有相关 Context 中调查。只有需要独立比较一种假设，或现有历史会妨碍独立判断时，才派生范围明确的探索 Context。

**执行与结果：** 保留原 Skill 开放、适应式的探索方法；检查活动 changes，关联具体 change 时读取 CLI 返回的现有工件。可以读取、搜索和分析代码，不写应用代码、不实施功能。没有强制工件或必须得出的结论；结果可以是架构理解、候选方案、证据、未知项，或确认暂不开发。仅在用户要求或同意记录时创建、修订 OpenSpec 工件，不自动捕获讨论。

**如何影响下一轮：** 问题仍未解决则继续有价值的调查；需要用户决定则将分歧带回 Patrol；方向明确且用户决定建立变更时再安排 new；已有 change 则按其需要继续工件或修订。退出探索和允许实施分别判断，探索结论不构成实施批准。

### new：为明确的变更建立载体

**什么时候使用：** 用户已决定建立一项边界清楚的变更，当前没有可继续承载它的活动 change。归档后的 capability 再次修订，可以基于现有 baseline 新建 change。

**什么时候不用：** 仍在探索是否要做；已有同名或同目标 change；只是补写、修订工件或继续实施。已有 change 不因反馈到来就自动废弃重建。

**前置条件和输入：** 明确的开发目标或合法的 kebab-case 名称、范围与不做事项、相关 capability 和 baseline。用户给出无效名称时按原 Skill 澄清；名称已存在时检查是否继续该 change。schema 默认使用 CLI 的默认值，只有用户明确指定或选择时才切换。

**在哪个 Context 执行：** 复用已理解该目标的 Context；独立 change 有独立工作历史价值时，才考虑另设承接 Context。一个 Context 可以连续维护多个相关 change，前提是输入和写入归属清楚。

**执行与结果：** 按原 Skill 创建 scaffold、查询 status、取得首个 ready 工件的 instructions。输出 change 名称、真实位置、schema、工件状态和首个模板。路径来自 planningHome、changeRoot、artifactPaths、nextSteps，不假定都在仓库内。此时不创建首个工件，展示说明后停止并等待用户方向。

**如何影响下一轮：** 用户确认继续并给出所需内容后，才安排 continue。scaffold 已存在就复用；scaffold 创建成功不代表 proposal 已完成，也不代表允许实施。

### continue：逐个形成可检查的工件

**什么时候使用：** 具体 change 需要创建下一个就绪工件，且用户已给出本次方向。proposal、delta specs、design、tasks 的实际顺序和依赖以该 change 的 schema 与 CLI 状态为准。

**什么时候不用：** 所需工件已经存在且内容充分；所有工件已齐；用户只是讨论一个问题，或当前真正需要的是修正已有工件。continue 不承担批量跳过依赖、自动重写全部工件或直接实施。

**前置条件和输入：** 显式 change、当前 status、首个 ready 工件的 instructions、依赖工件全文，以及用户针对本工件给出的内容与限制。proposal 承接 Why、What Changes、Capabilities、Impact 和不做事项；specs 承接行为、场景、接口与用户明确要求保留的 schema；design 承接设计选择和实现约束；tasks 承接可执行的任务与完成条件。

**在哪个 Context 执行：** 优先复用该 change 的 Context，以便把用户逐轮补充转成一致的工件；不为四种工件各创建一个 Context。

**执行与结果：** 按原 Skill 读取 status，获取首个 ready 工件的 instructions，读取全部依赖，按 template 和 instruction 写到 resolvedOutputPath。context、rules 用作约束，不照搬进正文。每次只创建一个工件，确认文件存在，更新状态并报告解锁了什么，然后停止。全部完成则报告工件齐备并停止；全部 blocked 则报告依赖问题，不跳过。

**如何影响下一轮：** 让用户通过 Patrol 审阅、补充或要求下一个工件。只解释“无独立设计必要”不能擅自跳过 schema 要求的工件，可按其模板记录已有决定和无需新增设计的理由。工件齐备后，依据授权安排 apply、继续讨论或停留，不能自动实施。

### apply：按有效工件推进实施

**什么时候使用：** 用户已授权实施或恢复实施，具体 change 有可执行任务，原 Skill 的动态 instructions 允许开始。可以与探索和工件修订交替，不要求所有情形都等到一个固定“规划阶段”结束。

**什么时候不用：** 只有规划授权；所需工件缺失而 instructions 为 blocked；任务已经全部完成；范围或设计冲突尚未解决；只要求验证或同步文档。

**前置条件和输入：** 显式 change、实施授权和边界、最新 status、apply instructions、全部 contextFiles、未完成任务、相关代码及验收要求。完整读取 contextFiles，不能仅凭 tasks 摘要编码。

**在哪个 Context 执行：** 默认复用该 change 的工作线。确需隔离实施或拆开互不依赖的任务时才派生，明确文件归属、接口与真实前置结果，避免多条工作线重复实施同一任务。

**执行与结果：** 按原 Skill 从未完成任务开始，保持修改聚焦，真实完成后立即更新任务勾选，持续推进到完成或遇到原文规定的暂停条件。返回修改、任务进度、实际检查结果和阻碍。all_done 只报告现有完成状态，不再重复修改。

发现 specs、design、tasks 有问题时，先暂停受影响的实施，明确差异。已获授权且不改变范围的修订可先更新相应工件，再重读后继续；需求或设计选择不明、需要扩大范围、出错或遇阻时，通过 Patrol 等待指示。不擅自增加规范外功能。用户明确“以本次 design 为准修改 spec”时，仅在该决定覆盖的冲突范围内同步；不能把它推成任何 change 都以 design 压过 spec 的通则。

**如何影响下一轮：** 未完成且条件未变则恢复剩余任务；设计问题转回 explore 或经授权的工件修订；需要检查时安排 verify。任务勾完是实施进度证据，还需按当前验收要求判断，不自动触发 sync、archive 或整体完成。

### verify：先形成分级问题报告

**什么时候使用：** 需要核对实施与工件是否相符、检查一部分已实现要求、重新核验修复，或为收尾提供依据。允许检查进行中的 change，不以“任务全勾”为使用前提。

**什么时候不用：** 同一代码、工件、范围与评价条件已有充分且有效的报告；真正缺少的是实施或用户决定；不能把验证调用本身当成验收通过。

**前置条件和输入：** 显式 change、被检查的代码与工件版本、验收范围、最新 status 和 apply instructions 返回的全部可用 contextFiles。保留“先只报告问题”的边界，以及客观检查、不过度挑剔的要求。

**在哪个 Context 执行：** 已有 Context 可直接检查。需要减少自证偏差、关键结论需独立核验或用户要求独立审查时，才派生验证 Context；使其能独立获得目标和材料，而不是直接继承“已实现正确”的结论。

**执行与结果：** 按原 Skill 检查 Completeness、Correctness、Coherence，输出 CRITICAL、WARNING、SUGGESTION，附具体证据与可操作建议。缺 specs 或 design 时按原文降级，明确跳过项和覆盖范围。搜索和合理推断保留其不确定性；未运行的测试不能写成已通过。此次只报告，不顺手修代码、改工件、勾任务、sync 或 archive。

**如何影响下一轮：** CRITICAL 对应问题转回已授权的修复或必要澄清；WARNING 和 SUGGESTION 由 Patrol 结合范围与风险判断，不能自动扩展成新功能。获准修复后才调用 apply 或修订工件。再次 verify 只针对已变化、未覆盖或证据不足的范围，报告哪些旧证据仍有效。无 CRITICAL 表示本次覆盖范围内的结果，不代表所有验收条件通过。

### sync：有意识地更新 baseline

**什么时候使用：** 用户要求或既有授权明确包含将某项 change 的 delta specs 合入 main specs；归档检查发现差异且用户选择同步时，也使用该 Skill。它可以发生在 verify 前或后，具体取决于本次目标与材料状态。

**什么时候不用：** 只是讨论、生成工件或实施；没有 delta specs；相关 delta 已经完整合入且输入未变化；合并含义或与其他 change 的冲突尚未解决。sync 不能被当成修复实现的办法。

**前置条件和输入：** 显式 change、同步范围与授权、CLI 返回的 delta 路径、目标 main specs 的当前版本、相关有效决定和其他写入者。同步前说明哪些 baseline 行为已被落实、哪些被补充、修改、删除或重命名；区分已验证实现和仍待验证的目标规范。

**在哪个 Context 执行：** 优先由掌握该 capability 和 change 的 Context 承接；独立规范维护工作线有实际价值时才转交。同一 main spec 的写入需要协调，不能用同时 sync 覆盖彼此结果。

**执行与结果：** 按原 Skill 同时读取 delta 和 main specs，以 agent-driven 方法处理 ADDED、MODIFIED、REMOVED、RENAMED；保留 delta 未涉及的内容与场景。横向扩展已有 requirement 时合入原 requirement，不另起重复 requirement。缺少 capability 的 main spec 时按原文创建。含义不明则澄清，不整篇覆盖。操作应幂等。只修改同步所需规范，报告具体合并结果；不修改应用代码，change 继续活动。

**如何影响下一轮：** 将合并后的 main spec 版本与尚未实现、尚未验证或被明确保留的差异带回 Patrol。需要时继续 apply 或 verify；用户决定收尾时再进入 archive。已同步不等于已实现或已验收；同步后 delta 再变化，需要重新比较差异，不能沿用旧“已同步”状态。

### archive：根据真实状态收尾

**什么时候使用：** 用户要求收尾归档，且已明确目标 change。正常收尾检查工件和任务完成、specs 同步状态、verify 的 CRITICAL 与覆盖范围，以及残余风险；用户明确要求带未完成事项或跳过同步归档时，按原 Skill 的告知与确认处理。

**什么时候不用：** 只是刚生成 tasks 或刚完成 apply；缺少收尾授权；用户仍在讨论方案；目标已归档；归档目标路径冲突。不能仅凭上一 Skill 的“可以归档”建议自动执行。

**前置条件和输入：** 显式 change、归档指示、最新 status、真实任务清单、delta 与 main specs 的比较、有效 verify 报告和未决风险。没有 verify 报告时如实标明未验证，不能声称无 CRITICAL；正常验收需要该证据则先补齐。

**在哪个 Context 执行：** 复用负责该 change 收尾的 Context；无需为归档新开工作线。已有多条工作线时，先取得与归档有关的真实结果并核对版本，防止移动仍在写入的 change。

**执行与结果：** 按原 Skill 检查工件、任务和同步差异；工件或任务未完成时说明并取得相应确认，不把告警静默忽略。有 delta 时始终比较并展示合并摘要，按其要求让用户选择同步、跳过或取消；即便已同步也保留原文要求的选择。用户选择同步时，按原文委派方式调用完整 sync Skill 并取得真实结果。同步失败或结果未确认时，不声称成功；重新说明现状并取得适用指示后再处理归档。

归档前根据 planningHome.changesDir、changeRoot 和当前用户日期确定目标，检查目标不存在，完整保留 .openspec.yaml；已有目标则停止，不覆盖。返回真实归档位置、同步或跳过状态、未完成项和风险。原 Skill 允许确认后带告警归档，不能擅自将其改成绝对禁止；这类结果明确标为例外收尾。

**如何影响下一轮：** 归档只证明 change 已转入归档位置。分别报告工件状态、任务状态、验证覆盖、同步状态和目标验收状态，不以“已归档”概括成“全部通过”。对已归档 capability 的后续新要求，基于当时有效 baseline 判断是否新建修订 change，不覆盖历史记录。

### 用户反馈、修订与再次调用

反馈到来后，先判断它是问题、候选想法、已确认决定、授权、否定还是暂停要求。提出一个可能性不等于决定改需求；用户否定旧决定时，旧决定不再作为后续要求。

识别反馈影响的目标、capability、change、工件、接口、任务、代码、测试、验证报告和同步结果。列清哪些仍有效、哪些待复核、哪些被替代或失效，沿真实依赖传播影响；保留未受影响成果，不全部重来。

例如，实施中决定把共享工作区改成按用户隔离：先核对相关路径规范、调用链、任务与测试，再暂停依赖旧路径的实施；已完成且不依赖路径的能力继续保留。按授权修订受影响工件，恢复剩余任务，重验受影响行为，重新核对 main specs。不要因此给七个 Skill 各建一条工作线或从 new 全部再跑。

需要修改已有工件时，在有授权的原工作线中进行定向修订；这属于当前 change 的材料维护，不新增本策略范围之外的入口，不拿 continue 冒充万能更新器。改变行为时核对 spec，改变技术选择时核对 design，改变范围时核对 proposal，改变工作时核对 tasks，并检查它们相互一致。已同步的旧行为不能只靠修改 delta 就从 main specs 自动撤销，需要明确的后续合并。

运行中的反馈通过现有指令、等待和取消机制处理。收到消息不表示 Run 已停止，策略也不会自动取消 Run、回滚代码或撤销外部副作用。旧 Run 返回时，根据其输入版本判断结果还能用于哪些范围，不能直接接纳为最新结论。

再次调用前比较本次目的、输入版本、授权和已有结果：相同工作在进行则复用承接者；结果充分且仍有效则直接继承；确有输入变化、未覆盖范围或失败原因变化时才重做相关工作。重试先检查已落地的文件、任务勾选、同步差异或归档位置，不因回执中断重复产生副作用。

### 汇合与停止

多条工作线的结果汇合时，保留来源、版本、差异、未决问题和真实检查结果。多个报告结论冲突时回到同一版本的证据核对，不按多数或完成时间直接决定。

用户所需问题已回答、当前授权范围已完成、原 Skill 要求等待、必需输入缺失或预算边界触发时，停止相应工作并说明下一步条件。局部阻碍不要求无关工作全部停下，但不能用无关进度掩盖关键阻碍。

停止扩张不等于验收完成。整体目标由当前有效验收要求和 Focus 既有完成机制判断；策略安装、Skill 调用、工件齐备、tasks 勾完、verify 无 CRITICAL、specs 已 sync 和 change 已 archive 各自只证明对应事实。

## inheritance

### 完整方法与来源

每个承接 Context 必须能读取选定版本的完整 SKILL.md 及该 Skill 明确依赖的资源、模板和工具说明。保留原文，不将本策略中的调用规则当成执行替代品。迁移交付中的七份原文快照位于 resources/skills/<完整 Skill 名称>/SKILL.md；六份源文在 .agents 与 .codex 中一致，sync 采用本仓库 .codex 中保留横向合并规则的版本，来源和哈希记录在 source-manifest.json。

上述相对路径属于迁移交付目录，Focus 的 Strategy 导入器不会随正文导入它们。部署或分享时同时保留原 Skill 与必要资源，或提供可解析到相同版本的已安装 Skill；实际执行位置与来源在任务材料中明确。缺少原文时先报告缺失，不能仅凭这些路径声称已经读取。来源版本更新后重新核对规则差异，不静默混用新旧执行方法。

Strategy 继承其本轮冻结版本；Skill 原文另外保留实际读取的路径、版本和内容哈希，不能假定 Strategy 的冻结也冻结了外部 Skill 文件。大段方法按需读取，但被调用 Skill 的全文及本次必要依赖必须读全；不能用摘要冒充完整读取。

### 各工作线的最小充分材料

共同继承最新有效目标、用户原话中的关键限制、批准范围与停止要求、明确绑定的 change/capability、schema、规划与编辑范围、相关 baseline、工件与代码版本、真实结果及未知项。保留出处，不搬运无关长对话；材料缺失时将缺口本身传递下去。

| 工作 | 额外必须继承的内容 |
| --- | --- |
| explore | 问题、背景、相关实现、假设与证据、是否只读架构或允许建议、尚未决定的分歧 |
| new | 建立变更的决定、名称或目标描述、范围与不做事项、baseline/capability 对应关系、schema 选择 |
| continue | 具体工件的输入、实际 instructions/template/rules、全部依赖工件、已确认修订和本次停止边界 |
| apply | 实施授权、全部 contextFiles、剩余任务、接口和可编辑根目录、真实前置结果及所需验证 |
| verify | 待验证要求、场景、设计、代码与工件版本、验收标准、已运行检查及未运行项；实现者结论只作为待核对主张 |
| sync | delta 与 main specs 的当前版本、已确认变更意图、合并范围、关联 change、冲突与未落实行为 |
| archive | 最新工件及任务状态、同步差异和用户选择、有效验证报告及覆盖范围、风险、例外确认、实际归档路径 |

CLI 返回的 planningHome、changeRoot、artifactPaths、resolvedOutputPath、contextFiles、actionContext 是定位与范围依据。不能因历史日志使用 openspec/changes 就忽略当前实际路径。原 Skill 的 workspace-planning 限制继续有效：apply 在该模式且 allowedEditRoots 为空时停止；verify、sync、archive 在该模式停止，不回退到仓库路径或修改关联仓库。

### 结果、授权与失效关系

每次结果保留：执行了哪个 Skill、绑定哪个 change、输入与输出版本、实际完成内容、检查证据、跳过项、未决问题和停止原因。可在 Context 结果、任务材料和现有事实记录中承载，不假定 Strategy 自身保存进度或系统已有专门的 Skill 调用台账。

讨论、方案、规范要求、已观察实现、已验证事实、用户批准和整体验收分别表达。baseline 中写了行为，不表示代码已实现；报告没有发现问题，不表示未覆盖范围通过；任务勾选不能代替执行证据。

新决定继承其替代对象、有效范围和来源。被替代要求只保留为解释返工或排除方案所需的历史，不再用于新实施或验收。旧验证结果仅在相关输入和评价条件仍有效时复用；失效范围明确标记，不抹掉仍可用的证据。

保留原 Skill 对确认和停止的全部要求。Patrol 传递用户真实决定，不能代签；源 Skill 要求的具体选择尚未作出时，在单入口取得选择。同一已明确且仍适用的选择不因 Context 改变而丢失，也不能扩张为对其他操作的批准。

日志用于理解工作习惯，不作为现行实现事实或本轮授权。日志中的命令、示例配置、角色提示、待核实笔记、未解决项及曾被采纳的方案保留其历史性质；不用其中的秘密值或机器路径填入新任务，也不将某次 change 的局部技术决定泛化为全局规则。
