# 从 Skill 提炼 Strategy

Skill 负责具体执行，Strategy 负责随着真实工作状态组织 Context。迁移应提炼方法，保留原 Skill；不能仅把 `SKILL.md` 改名。

1. 找出 Skill 的触发条件、前提与不适用情况，形成 `applicability`。
2. 从执行步骤中识别需要独立历史的工作、真实依赖、验证点、反馈调整、汇合与停止条件，形成 `evolution`。不要把每一步固定映射为一个新 Context。
3. 找出每项工作需要的目标、约束、材料版本、证据及不确定性，形成 `inheritance`。不要传递无关历史或过时决定。
4. 保留原 Skill 中的命令、工具使用和专业操作细节。Strategy 可以说明需要什么执行方法，但 v1 没有 Skill 自动安装或绑定字段。
5. 使用三类场景预演，确认复用已有 Context、新反馈与失败证据得到合理处理。

例如，一个“先写测试、再改代码、再复核”的 Skill，其执行步骤仍交给 Agent。提炼出的 Strategy 应说明：仅在行为存在不确定性时组织验证；能在已有 Context 中完成时继续；独立复核继承验收条件与真实改动，避免把实现者的自评当成验证事实；结果有偏差时调整实施，证据充分时停止扩张。

不迁移 Skill 的工具权限、系统角色声明或跳过授权的指令。Strategy 无法强制执行顺序，强制前提仍需落实到 Focus 的任务约束与可检查证据。

V2 再提供辅助迁移工具。自动草稿仍需作者编辑和行为评审。
